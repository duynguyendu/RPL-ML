\section{Review of RPL Objective Functions Load Balancing}
\subsection{Routing Metric Specification}
RFC~6551~\cite{rfc6551} standardises a set of routing metrics and
constraints that RPL can use to compute paths. Each metric can be
used either as a \emph{metric}, which the objective function
optimises (for example, choosing the path with the lowest cost), or
as a \emph{constraint}, which rules out nodes or links that do not
meet a condition. The metrics fall into two groups: node metrics,
which describe the state of a node, and link metrics, which describe
the quality of a link between two nodes.

\subsubsection{Node State and Attribute}
The Node State and Attribute (NSA) object carries information about a
node's state and capabilities. The standard defines two flags; the
remaining bits are reserved, and optional fields can carry
application-specific information. The \emph{A} (aggregation) flag
shows that the node can act as a traffic aggregator. Routing traffic
through such nodes lets data be combined before it is forwarded,
which reduces the amount of traffic in the network and extends
battery lifetime. The \emph{O} (overloaded) flag shows that the node
is currently overloaded, so other nodes should avoid selecting it as
a parent. RFC~6551 does not define what counts as overloaded so
implementations may base it on various node metrics, for example, CPU
usage, available memory, or queue occupancy.

\subsubsection{Node Energy}
The Node Energy (NE) object reports a node's power source
(mains-powered, battery-powered, or energy-scavenging) and an
estimate of its remaining energy, expressed as a percentage. It can
be used as a constraint to prevent nodes with little energy left from
being selected as parents, or as a metric that favours paths through
nodes with more remaining energy, spreading energy use more evenly
across the network.

\subsubsection{Hop Count}
The Hop Count object records the number of hops along the path from a node to
the root. It is simple to compute and adds almost no overhead. However, it
says nothing about link quality, so on its own it tends to favour long,
unreliable links.

\subsubsection{Throughput}
The Throughput object reports the throughput of the links along a path, in
bytes per second. It can be used to choose paths with enough capacity for
the
traffic they will carry.

\subsubsection{Latency}
The Latency object reports the delay along a path. It can be used as
an additive metric (the total latency of the path) or as a
constraint, for example to exclude paths whose latency exceeds a
delay bound required by the application.

\subsubsection{Link Quality Level}
The Link Quality Level (LQL) is a coarse measure of link reliability,
encoded as an integer from 0 to 7. A value of 0 means the quality is
unknown, 1 is the highest-quality link, and 7 the lowest. How the
level is computed is left to the implementation; it may be derived
from, for example, the packet error rate or the received signal strength.

\subsubsection{Expected Transmission Count (ETX)}
The Expected Transmission Count (ETX)
number of transmissions, including retransmissions, needed to deliver a
packet
over a link and receive its acknowledgement. It is calculated as
\begin{equation}
    \mathit{ETX} = \frac{1}{D_f \times D_r},
\end{equation}
where $D_f$ is the forward delivery ratio, the probability that a packet is
received by the neighbour, and $D_r$ is the reverse delivery ratio, the
probability that the acknowledgement is received by the sender. A perfect
link has an ETX of $1$, and the ETX grows as the link becomes lossier.

\subsubsection{Link Colour}
The Link Colour object is a 10-bit field that an administrator can
use to mark links with particular properties. Traffic of a given type
can then be steered towards, or away from, links of a certain colour,
for example to keep critical traffic on encrypted links.

\subsection{Load Balancing Objective Function}
Numerous objective functions have been proposed to address load
balancing in RPL. According to their parent selection strategy, these
can be grouped into four categories. \emph{Composite-metric} approaches
combine several metrics, such as queue utilisation, residual energy and
ETX, into a single cost through a hand-set formula or rule set, and
select the parent with the lowest cost. \emph{Probabilistic} approaches
distribute traffic across multiple parents by selecting each next hop at random
based on weighted probabilities instead of selecting one ``best''
parent. \emph{Reinforcement learning} approaches learn the cost of
each candidate parent online from the
observed outcomes of previous transmissions.

Finally, \emph{supervised
machine learning} approaches train a model on collected network data to
score or rank candidate parents. Unlike composite-metric approaches,
these models learn the relative weighting of metrics from training data
rather than relying on manually tuned values. The remainder of this
section reviews representative work in each category.

\subsubsection{Composite-metric OF}

Kim et al.~\cite{kimQURPLQueueUtilization2015} observe that most
packet losses in heavy traffic networks are caused by queue overflow
rather than by link failures. Based on this observation, they propose
QU-RPL, a queue-utilisation-based extension of RPL. In QU-RPL, nodes
advertise their queue utilisation factor, which is defined as
\begin{equation}
    Q(k) = \frac{\text{Number of packets in queue}}{\text{Total queue size}}
\end{equation}
where $Q(k)$ is the queue utilisation factor of node k. The $Q(k)$ is
smoothed using
exponentially weighted moving average (EWMA) filter to make it robust
against sudden change and fluctuation. A node uses
this queue utilisation information from DIO messages together with
hop count to avoid parents whose queues are nearly full while
selecting parent that is closer to root.
QU-RPL also changes the Trickle timer so that a node resets its timer
after several consecutive queue losses. This allows a node to
advertise its congestion quickly, and its neighbours can adapt their
parent choices without waiting for the next scheduled DIO. With these
changes, QU-RPL achieves a lower queue loss ratio and a more balanced
routing tree than standard RPL. However, the parent decision depends
mainly on queue utilisation and gives little weight to link quality.
A node may therefore move to a parent with a free queue but a poor
link, which avoids queue loss at the cost of more link-layer losses
and a lower packet delivery ratio.

Gaddour et al.~\cite{gaddourOFFLQoSawareFuzzy2014} propose OF-FL, an
objective function that uses fuzzy logic to combine several routing
metrics with the aim to support applications with different
requirements. OF-FL considers four metrics: hop count, end-to-end
delay, ETX and remaining battery level. Each metric is mapped onto
linguistic labels through membership functions, and a set of fuzzy
rules combines these labels into an overall quality for each
candidate parent, ranging from awful to excellent. Simulation results
show that OF-FL achieves a higher packet delivery ratio and lower
energy consumption than the standard objective functions.
However, its membership functions and rule base are designed by hand
and may therefore embed designer bias. Moreover, the rule base grows
exponentially with the number of input metrics and linguistic labels,
making it difficult to incorporate additional metrics.

Abreu et al.~\cite{abreuEnergyawareRoutingBiomedical2014} propose the
Energy-Aware Objective Function (EAOF) for healthcare monitoring
applications, where energy efficiency is a primary concern. Conventional
objective functions favour the most reliable routes, which lead to
hot spots and drain batteries of those nodes quickly. EAOF addresses this by
combining ETX
with the remaining energy of each candidate parent, so that paths
through nodes with more battery left are preferred. EAOF accepts a
small reduction in packet reception in exchange for more balanced
energy consumption and a longer network lifetime. Its main limitation
is that remaining energy is a lagging indicator of load.
% TODO:  validate this claim
A node's battery level falls slowly and reflects the traffic it has already
forwarded, not the traffic it is forwarding now. EAOF therefore
reacts only after an imbalance has already used up energy, and it
cannot detect short-term congestion such as queue overflow at a
heavily loaded parent. Early in the network's life, when all nodes
have similar energy levels, EAOF behaves much like an ETX-based
objective function, so hot spots can still form.

Taghizadeh et al.~\cite{taghizadehCLRPLContextAwareLoad2018} propose
Context-Aware and Load Balancing RPL (CLRPL). Its objective function
uses an energy index that covers the entire chain of parents up to
the root instead of the immediate parent. The index is computed
recursively, and a decay factor reduces the influence of each node
farther up the chain, so a depleted node affects
the nodes below it only weakly. The rank is then computed by this
energy index with the ETX to the parent. Finally, CLRPL combines the
rank with the Context-Aware Routing Metric (CARF), which is a queue
utilisation metric along the parent chain in the same recursive,
decaying calculation as energy index,
to select the best parent.
To avoid the thundering herd problem, a node does not advertise its
real rank straight away. It starts with the highest rank it has heard
from its neighbours and lowers it gradually, one step per DIO
interval, until it reaches its real rank.
Simulations shows that CLRPL produces a more balanced DODAG with
smaller subtrees' size and reduces congestion, packet loss and
number of parent changes.
However, CLRPL is evaluated with MAC duty cycling disabled, so every
node's radio stays on for the whole simulation. Because the radio
accounts for most of a node's energy consumption, every node spends energy at
nearly the same rate regardless of the traffic load. As a result,
the energy index is likely to vary little between nodes and the
reported improvements probably come mainly from ETX and queue utilisation.
In addition, the authors do not explain why queue utilisation is kept
out of the rank calculation. In RPL, a node recalculates its rank each
time it receives a DIO from its parent, so receiving queue
utilisation in the DIO and recomputing rank happens at the same moments.

\subsubsection{Probabilistic OF}
Liu et al.~\cite{liuLoadBalancedRouting2013} propose LB-RPL, which adds two
load-balancing mechanisms to RPL while still taking link quality into
account. First, each node keeps a table of its top $k$ candidate
parents and spreads its traffic across them, not sending everything
through a single preferred parent. Each packet is forwarded to parent
$j$ with probability $f_{ij}$
\begin{equation}
    f_{ij} = \frac{(1 - p^{c}_{ij})}{\sum_{j=1}^{k} (1 - p^{c}_{ij})}
\end{equation}
where $p^{c}_{ij}$ is packet drop probability due to link condition
between node $i$ and node $j$. This means that the traffic is spread across the
$k$ parents, with parents that have better links being chosen more often.
Second, a node signals its workload by delaying its DIO messages in
proportion to its buffer utilisation. Heavily loaded nodes therefore
advertise themselves later than lightly loaded ones and are less
likely to be selected as parents by their neighbours. Because this
signal is carried by the timing of existing messages, it adds no
extra control overhead. In simulation, LB-RPL achieves a higher
packet delivery ratio and lower latency than standard RPL, and it
substantially reduces the workload of nodes near the root.
The authors do not give how to calculate drop probability.
However, the authors do not specify
how the drop probability $p_{j}^{c}$ is calculated, which makes the
scheme difficult to reproduce. Additionally, using delayed DIOs as a signal
of load can slow the spread of routing information and delay route
repair in exactly the parts of the network that are congested.

Homaei et al.~\cite{homaeiLoadBalancingIoT2025} propose Learning
Automata-based Load-Aware RPL (LALARPL), which uses learning automata
to spread traffic across several parents. Each parent advertises a
Traffic Index (TI), which measures how much of its capacity is being
used,
\begin{equation}
    TI_i = \frac{\sum_{k} \theta_{ki} \, T_k}{CB_i},
\end{equation}
where $T_k$ is the total traffic that child $k$ send, $\theta_{ki}$
is the fraction of child $k$'s traffic $T_k$
routed through parent $i$ and $CB_i$ is the bandwidth available to
$i$. The TI is advertised along with the parent's hop count and
remaining energy in extended DIO messages. Using this information,
each node builds a small set of candidate parents, excluding those
that are nearly out of energy. For each packet, a learning automaton
chooses a parent from this set based on each parent's traffic index
and hop count relative to the other candidates. The initial
selection probability of parent $i$ is
\begin{equation}
    P_i = \zeta \, \frac{1/\mathrm{hop\_count}_i}{\sum_{j=1}^{N}
    1/\mathrm{hop\_count}_j} + (1-\zeta)\, \frac{TI_i}{\sum_{j=1}^{N} TI_j},
\end{equation}
where $N$ is the number of candidate parents and
$\zeta \in [0,1]$ weights hop count against traffic index.
Parents periodically reply with an acknowledgement carrying their
current TI. A parent is rewarded if its TI is low compared with the
other parents in the set and penalised if it is high. The selection
probabilities are then updated using the linear reward--penalty
scheme. When parent $i$ is rewarded,
\begin{equation}
    p_i \leftarrow p_i + \alpha (1 - p_i), \qquad
    p_j \leftarrow (1 - \alpha)\, p_j \quad \forall j \neq i,
\end{equation}
and when it is penalised,
\begin{equation}
    p_i \leftarrow (1 - \beta)\, p_i, \qquad
    p_j \leftarrow \frac{\beta}{N-1} + (1 - \beta)\, p_j
    \quad \forall j \neq i,
\end{equation}
where the reward and penalty rates $\alpha$ and $\beta$ are
recomputed at each update from the parent's TI and hop count. Over
time, nodes therefore learn to prefer lightly loaded parents.
LALARPL also lengthens the Trickle interval when traffic is heavy,
which reduces control overhead during congestion. In simulation,
LALARPL improves packet delivery ratio, throughput and delay compared
with several other load-balancing protocols. Despite that, the reward
depends only on how heavily each parent is
loaded, not on link quality, and lost packets give no feedback at
all. Moreover, the authors do not specify how the child's $k$ traffic
contribution calculated and do not evaluate the network overhead of
the acknowledgements that parents send to update the learning
automata.

Acevedo et al.~\cite{acevedoWRFRPLWeightedRandom2021} propose
Weighted Random Forward RPL (WRF-RPL), an objective function that
spreads traffic by choosing the next hop at random according to a
weighted score, similar to LB-RPL and LALARPL. WRF-RPL sets the
$\mathit{Rank\_Increase}$ to a fixed value of 1, so a node's rank
equals its hop count to the root. Each candidate is given a weight
based equal its remaining energy percentage, and the next hop is
drawn at random in proportion to these weights. Nodes with more
remaining energy are
therefore more likely to be chosen. Nodes with less energy can still
be selected, but less
often, so no single relay is used all the time. This spreads traffic
across the available parents, reduces congestion and prevents any one
relay from being used repeatedly.
The authors acknowledge that the performance of WRF-RPL depends on the
topology. Networks with many
intermediate nodes offer more candidate parents and can therefore
spread the load more evenly, whereas in networks made up mostly of
leaf nodes there are few alternatives to choose from. WRF-RPL also
has other limitations. Because rank is based only on hop count and
parent selection is then based on remaining energy, the
protocol ignores link quality and may forward traffic over lossy
links, which increases retransmissions. Like EAOF, it relies on
remaining energy, which changes slowly, so it cannot react to
short-term congestion such as queue overflow at a parent.

\subsubsection{Reinforcement learning}
% TODO: how to link between q learning and ML of the same author
Duenas Santos et al.~\cite{duenassantosQRPLQLearningBasedRouting2024}
propose Q-RPL, which brings Q-learning into the objective function.
In Q-RPL, each node learns a value for each of its candidate parents
from the actual outcome of the packets it sends. When a transmission
succeeds, the agent receives
a reward based on the number of transmissions needed to reach the
next hop and is penalised when choosing a parent leads to packet loss.
Nodes begin by selecting parents at random to explore
their options, and then gradually shift towards the parent with the
highest learned value. Each node also includes its Q-value in its DIO
messages, so neighbouring nodes can take it into account when
selecting their own parents. In addition, ETX and RSSI are used to
filter out unsuitable candidates and to break ties between parents
with similar values. The authors report that the learned behaviour
settles after roughly two to three hours of operation. However, this
long convergence period is itself a limitation. While the agent is
exploring, nodes may select poor parents, which leads to packet loss
and wasted energy. The paper does not measure this cost, and it does
not report the memory or computational overhead of running Q-learning
on constrained devices. Moreover, because the reward depends only on
the number of transmissions to the next hop, it mainly reflects the
quality of each link. It does not directly capture congestion or load
at the parent, so Q-RPL is not designed specifically for load balancing.

Farag and Stefanovic~\cite{faragCongestionAwareRoutingDynamic2021}
propose a Q-learning approach to congestion-aware parent selection in
RPL. Each node maintains a Q-value $Q_x(y)$ for every neighbour $y$,
representing the cost of routing through that neighbour. The cost
signal combines the neighbour's queue occupancy, the link quality and
the neighbour's hop count:
\begin{equation}
    R(y) = \lambda(y)\,\mathrm{BF}(y) + \mathrm{ETX}(x,y) + H(y),
\end{equation}
where the backlog factor $\mathrm{BF}(y)$ is the fraction of $y$'s
queue currently occupied, $H(y)$ is its hop count, and $\lambda(y)$
amplifies the backlog term once $\mathrm{BF}(y)$ exceeds a threshold.
Under light load the cost is therefore dominated by ETX and hop count,
whereas under heavy load congested parents become expensive. The
backlog factor is encoded together with the hop count in the RANK
field of DIO messages, so no new control messages are required, and
a node resets its Trickle timer after several consecutive queue
losses so that congestion information spreads quickly. On receiving
a DIO, a node updates the corresponding Q-value as
\begin{equation}
    Q_x(y) \leftarrow Q_x(y) + \alpha \left[ R(y) - Q_x(y) \right].
\end{equation}
The Q-value is thus updated from the state advertised by each
neighbour rather than from the outcome of the node's own forwarding
decisions, and each node learns to prefer parents whose queues are
less full. To avoid the thundering herd problem, parents are
selected probabilistically using a softmax-based strategy that
favours the neighbour with the lowest Q-value. Although described as
reinforcement learning, the update
rule has no discount factor or next-state term, so each Q-value is
simply a smoothed estimate of the immediate cost of a neighbour
rather than of future rewards. The evaluation uses
Monte Carlo simulations in MATLAB rather than an established network
simulator such as Cooja or ns-3, so the fidelity of its radio, MAC
and Trickle models cannot be verified, and the results are not
directly comparable with those of other RPL studies. Finally, the
method is evaluated only between 30 and 120 packets per minute per
node, loads already heavy by LLN standards, so its behaviour under
the light-to-moderate traffic typical of many WSN deployments is
untested.

Sangeetha et al.~\cite{sangeethaFederatedLearningBasedParent2025}
propose a novel method to incorporate
federated learning to train a parent-selection model while the
network is running. The model is a multilayer perceptron (MLP) that
takes four inputs: ETX, hop count, residual energy and delay; and
predicts the energy cost of routing through each candidate parent. Each
node trains the model on its own local data and sends the updated
weights to the root. The root combines the weights from all nodes
into a global model and sends it back to the network in DIO messages.
The output of each node is a lightweight vector summarisation, which
does not increase the overhead of the network too much.

The authors report lower energy consumption and a longer network
lifetime than OF0 and MRHOF. However, several aspects of the
evaluation raise doubts about whether the method would work on real
devices. First, the experiments use the Cooja mote type, which
compiles the firmware for the host machine and runs it natively. Code
running on Cooja motes is therefore not limited by the processing
power or memory of real sensor hardware, so the results do not show
that the MLP can be trained or run on a constrained device.
Second, the authors estimate energy consumption on Tmote Sky devices
from Energest measurements taken on Cooja motes. Cooja motes do not
emulate the Sky's MSP430 microcontroller, so the time spent running
code, including training and running the MLP, is not modelled
realistically. The CPU component of the energy estimate, which is
where the cost of the learning model would appear, is therefore
unlikely to reflect the energy a real Sky would consume.

\subsubsection{Supervised Learning OF}

Little research has applied supervised machine learning to parent
selection in RPL. To the best of our knowledge, the main body of work
consists of three related papers by Duenas Santos, Mezher and
colleagues, which proposed three related
schemes: RPL+~\cite{duenassantosRPLImprovedParent2022},
GNB-RPL~\cite{mezherGNBRPLGaussianNaive2023} and
ML-RPL~\cite{santosMLRPLMachineLearningBased2023}. All three use
machine learning to predict how likely a packet is to be forwarded
successfully over each hop.

In RPL+, the authors collect per-hop data from simulations and train
a decision tree to rank the importance of six candidate metrics: ETX,
channel utilisation, node density, throughput, queue utilisation and
MAC-layer losses \cite{duenassantosRPLImprovedParent2022}. The
resulting importance scores become the
coefficients of a linear equation that combines these metrics into a
single score for each candidate parent.
The $\mathit{Rank\_Increase}$ is fixed at 1, so a node's rank equals its
hop count to the root, and the parent with the lowest score is
selected. RPL+ improves the packet delivery ratio and
end-to-end delay compared with standard RPL. The machine learning
model is only used to analyse the feature importance without being
incorporated into the OF. Furthermore, a decision tree can capture
non-linear relationships
between the metrics and delivery, but RPL+ uses only its importance
scores as weights in a linear combination, which cannot express these
relationships.

Building on RPL+, GNB-RPL uses a Gaussian Naive Bayes classifier,
trained on the same features as RPL+, to predict the probability that
a packet will be delivered successfully to a candidate parent
\cite{mezherGNBRPLGaussianNaive2023}.
Unlike RPL+, which used to calculate the coefficients in path cost
equation, GNB-RPL is trained on a larger dataset and runs the
classifier inside the objective function itself, so that parent
selection is based directly on the output of the model.
However, the model rests on two strong assumptions. The Gaussian form
assumes that each feature follows a normal distribution, but metrics
such as ETX and queue utilisation are bounded and often skewed. The
naive Bayes form assumes that the features are independent of one
another, although several of them are clearly related, such as ETX
and MAC-layer losses, or channel utilisation and node density. When
these assumptions do not hold, the predicted probabilities may be
poorly calibrated. Moreover, the evaluation does not
include OF0, so it is unclear how GNB-RPL compares with the simplest
standard objective function.

Later on, the authors introduce
ML-RPL~\cite{santosMLRPLMachineLearningBased2023}, which replaces the
Naive Bayes classifier with a CatBoost model, a gradient-boosted
decision tree ensemble. The model learns from eight metrics: hop
count, ETX, MAC-layer losses, node density, channel utilisation,
throughput, queue utilisation and RSSI. Unlike GNB-RPL,
gradient-boosted trees assume neither normally distributed features
nor independence between them, so the model can capture non-linear
relationships and interactions between the metrics.
Although ML-RPL performs better than MRHOF and RPL+ in terms of PDR and delay,
the evaluation does not examine the costs of running the
model on constrained devices. It reports neither energy consumption
nor CPU utilisation, and it does not discuss the size of the model.
This is a significant omission for gradient-boosted ensembles, which
usually contain hundreds of trees and may exceed the few kilobytes of
RAM and limited flash available on typical sensor nodes.

The main limitation of these three papers is that they consider only
whether a packet is delivered over a single hop, not whether it
reaches the root over the whole route. Their training labels record
per-hop delivery only, so the models cannot learn how conditions
further up the DODAG affect a packet. As a result, a node may select a
parent with an excellent link whose own path to the root is congested
or lossy. For example, the parent may forward its traffic through an
overloaded node near the root, where packets are dropped by queue
overflow. The first hop then looks reliable even though few packets
reach the root. Maximising per-hop delivery therefore does not
necessarily maximise end-to-end delivery, which is what ultimately
matters to the application. This is particularly important for load
balancing, since the hot spots that cause packet loss are usually
close to the root rather than at the first hop.
