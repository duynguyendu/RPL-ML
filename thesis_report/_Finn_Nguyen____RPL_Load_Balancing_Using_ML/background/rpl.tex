\section{Routing Protocol for Low-Power and Lossy Networks (RPL)}

RPL is an distance-oriented vector routing protocol that builds a
Destination-Oriented Directed Acyclic Graph (DODAG) over IEEE
802.15.4 PHY/MAC layers and 6LoWPAN \cite{alexanderRPLIPv6Routing2012}.
It is primarily designed for Wireless
Sensor Networks (WSNs),
where multipoint-to-point traffic toward one or more roots is the
dominant communication pattern.
Routes in RPL are optimised for traffic to or from one or more
roots in the topology, while maintaining reliable and energy
efficient data collection. To maintain reliable and energy-efficient
data collection, RPL is designed to adapt to changing
network conditions, allowing nodes to switch routes when route
degradation is detected.

\subsection{Destination-Oriented Directed Acyclic Graph (DODAG)}
RPL organises nodes under a DODAG, with the WSN's sink
node often serving as the root of DODAG. A node forwards packets
toward the root by relaying them to its
parent, which in turn relays them further up the tree until they reach the root.
In a multi-sink deployment,
each sink node serves as the root of its own separate DODAG.
Within a DODAG, each node maintains a rank value, which is an estimation of the
distance between itself and the DODAG root.
A node may only choose a neighbour with a lower rank than its own as
its parent. As a result, rank strictly increases along every path away
from the root, the root has the lowest rank in the DODAG, and the
parent relationships form a hierarchy directed towards the root, as
illustrated in Figure~\ref{fig:dodag-example}.

A node's rank is computed by an objective function (OF), which
translates one or more routing metrics into a rank value and defines
how a node selects its preferred parent. The RPL
specification does not mandate a single OF for all applications.
Instead, it separates its core routing operation, such as DODAG
construction and maintenance from from route optimisation, which is
delegated to the OF. Each deployment can therefore choose the OF that
best fits its requirements, such as minimising energy consumption,
reducing latency, or favouring high-quality links. RPL also allows having
several DODAGs within the same network, each with its
own OF, so that different types of traffic can be routed according to
different objectives. This flexibility allows RPL to support a wide range of LLN
applications without changing the protocol itself.

During DODAG construction, each node selects a parent from a pool of
candidate parents, which are neighbouring nodes that have already joined the
DODAG. For each candidate parent $P$, the note $N$ computes the rank
it would have if it chose $P$:
\begin{equation}
    \mathit{Rank}(N) = \mathit{Rank}(P) + \mathit{Rank\_Increase}
\end{equation}
where $\mathit{Rank}(N)$ is the resulting rank of the node $N$,
$\mathit{Rank}(P)$ is the rank advertised by the candidate parent $P$,
and $\mathit{Rank\_Increase}$ is a positive value computed by the OF
that represents the cost of using $P$ as a parent. Because
$\mathit{Rank\_Increase}$ is always positive, a node's rank strictly increases
with each hop away from the root. How $\mathit{Rank\_Increase}$ is computed
and how parent is selected depends on the OF in use,
as discussed later in this chapter.

RPL introduces four main types of control messages to form
and control DODAG, as specified in ICMPv6 via RFC 6550
\cite{alexanderRPLIPv6Routing2012}
\begin{itemize}
    \item DODAG Information Object (DIO): advertises the DODAG,
        and carries information that
        allow nodes to discover a RPL instance, select parents and
        maintain the DODAG.
    \item DODAG Information Solicitation (DIS): solicits a DIO from
        neighboring nodes e.g. when when a node wants to discover or
        join a DODAG.
    \item Destination Advertisement Object (DAO): propagates
        information upward to root or parent to establish downward route.
    \item Destination Advertisement Object Acknowledgement (DAO-ACK):
        an optional message from root or parent to acknowledgement
        the received DAO.
\end{itemize}

To begin the DODAG forming process, the root node sends its DIO to
its neighbouring nodes, carrying RPL identifiers and any
additional metrics required by the OF. Upon receiving DIO, a node
compares its rank with the advertised rank and filters out ranks that
are higher then its own to prevent loop formation. Afterward, the node decides
whether to join the advertised DODAG or not.
In certain implementations, nodes wait for several DIOs, building
the pool of candidate parents before deciding.
After joining DODAG, the node computes the path cost of the
corresponding link for each candidate and determines the preferred
parent according the OF's policy. Once a parent has been selected,
the node broadcasts its own DIO to
advertise itself to its neighbours. This process is repeated
outward through the network until every node has join the DODAG.

DIOs are crucial in maintaining DODAG. Nodes send DIOs periodically to
advertise their rank and routing metrics. Each time a node receives a
DIO, it update the candidate parent set and
recompute its rank through each candidate in the same way as when it
first joined the DODAG. If the node switches its
preferred parent or its rank changes, it sends a new DIO to spread
the update down the DODAG. This lets the DODAG adapt as link
conditions and traffic change.
Despite that, frequent DIO would be redundant in consistent network
conditions, thus RPL employs Trickle timer to regulate the emission
of DIO based on network consistency.

A node can also send a DIS message to request DODAG information instead
of waiting passively for a periodic DIO. To refresh information from a
known neighbour, such as its preferred parent, the node sends a unicast
DIS. The neighbour must then reply with a unicast DIO and must not reset
its Trickle timer, so the rest of the network is not disturbed. To
discover the DODAG and its neighbours, for example when joining, the
node instead sends a multicast DIS. Every neighbour that receives it
resets its Trickle timer, so the node soon receives DIOs from all
nearby DODAG members. In both cases, the node processes these DIOs in
the same way as periodic DIOs.

Once a node has joined a DODAG, it sends a DAO to advertise that
it can be reached in the downward direction. The recipient of DAO
depends on the DODAG's Mode of Operation (MOP). In
\emph{storing mode}, the node unicasts its DAO to its preferred
parent. Each parent stores a route to the node and forwards the
information further up the DODAG. As a result, point-to-point (P2P)
traffic only needs
to travel up to the first common ancestor of the source and the
destination before it is routed down. In \emph{non-storing mode},
nodes do not keep downward routes. Each node instead sends its DAO
directly to the root, which maintains the full set of downward routes
and uses source routing to reach each node. All P2P traffic must
therefore pass through the root, which increases path length and the
load on the root. A node can request an acknowledgement by setting a
flag in its DAO. The receiver, which is the parent in storing mode or
the root in non-storing mode, then replies with a DAO-ACK, and if no
DAO-ACK arrives, the node retransmits the DAO.

\subsection{Trickle Timer}
Trickle timer is a scheduling algorithm based on consistency model.
The algorithm is structured in a way that would promptly send out DIO
during the formation process and would slow down when the DODAG has
been stabilised to reduce redundant DIO transmission \cite{rfc6206}.

The Trickle timer does this by evaluating the consistency of the
network message with its own state.
When the network information is consistent, it
exponentially increases the transmission interval of DIO. However,
upon detecting inconsistencies, trickle timer reset its send interval
to boost DIO transmission to spread the latest information to the
rest of the DODAG.
However, the RPL standard does not fully define what counts as an
inconsistency.
It lists a minimum set of events that must restart the
Trickle timer: joining a new DODAG version, receiving a multicast
DIS, and detecting a routing loop; and lets the implementations add
their own definitions of inconsistency. Contiki-NG, for example,
resets Trickle timer when a node's rank change by more than a threshold.

Trickle Timer employs three configuration
parameters to determine the sending window of DIO: $I_{\mathrm{min}}$,
$d$ (the specification use $I_{\mathrm{max}}$ to denotes this) and
$k$ as shown in Table~\ref{tab:tricker_timer_params}.
The maximum sending interval time
$I_{\mathrm{max\_time}}$ is calculated as:
\begin{equation}
    I_{\mathrm{max\_time}} = I_{\mathrm{min}} \times 2^{d}
\end{equation}

    \caption{Trickle Timer Parameters}\label{tab:tricker_timer_params}

        \begin{tabular}[c]{@{}p{0.22\linewidth}p{0.10\linewidth}p{0.58\linewidth}@{}}
            \hline
            \textbf{Parameter} & \textbf{Symbol} & \textbf{Description} \\
            \hline
            Min interval length & $I_{\mathrm{min}}$ & The minimum
            length of the Trickle interval \\
            Max doubling interval & $d$  & The maximum number of
            times that the interval can double \\

            DIOs a node must hear in within the current interval
            before suppressing its own DIO transmission \\
            \hline
        \end{tabular}
    \end{center}
\end{table}

The Trickle algorithm controls the transmission interval $I$, which
always stays within $[I_{\mathrm{min}}, I_{\mathrm{max\_time}}]$. In RPL,
the initial interval is usually $I = I_{\mathrm{min}}$.
At the start of each interval, Trickle sets a consistency counter $c$
to $0$ and picks a
transmission time $t$ uniformly at random from $[I/2, I)$. During the
interval, the node increments $c$ each time it hears a consistent
message from the neighbours. At time $t$, the node sends its DIO only if
$c < k$; otherwise, it suppresses its own transmission. When the interval
ends, Trickle doubles its interval length, up to the maximum:
\begin{equation}
    I = \min(2 \times I,\ I_{\mathrm{max\_time}})
\end{equation}
If the node detects an inconsistency while $I > I_{\mathrm{min}}$, it
resets $I$ to $I_{\mathrm{min}}$ and starts a new interval.
In this way, DIOs are sent frequently while the network is changing and
increasingly rarely once it has stabilised.

\subsection{OF0 and MRHOF}
Up to now, the IETF ROLL working group has standardised only two
objective functions: Objective Function Zero (OF0) \cite{rfc6552} and
Minimum Rank with Hysteresis Objective Function (MRHOF) \cite{rfc6719}.

OF0 was developed to be a simple objective function that utilises step
of rank, which is an intermediate computation based on link
properties of a certain neighbour. It computes $\mathit{Rank\_Increase}$ as
\begin{equation}
    \mathit{Rank\_Increase} = (\mathit{Rf} \times \mathit{Sp} +
    \mathit{Sr}) \times \mathit{MinHopRankIncrease}
\end{equation}
where $\mathit{Rf}$ (Rank Factor) is a small positive integer used to scale
the step of rank, $\mathit{Sp}$ (Step of Rank) is an integer value
that represents the cost of the link to the parent, acting as an
abstract hop count, and $\mathit{Sr}$
(Stretch of Rank) is an optional value that is used to inflate
$\mathit{Rank\_Increase}$ so more neighbours qualify as feasible parents.
With $\mathit{Rf} = 1$, $\mathit{Sp} = 1$ and $\mathit{Sr} = 0$,
$\mathit{Rank\_Increase}$ becomes a fixed increment of $256$ per hop
(the default $\mathit{MinHopRankIncrease}$) so OF0 behaves like a
OF that uses pure hop-count metric. However, the OF0 specification strongly
recommends deriving $\mathit{Sp}$
from Expected Transmission Count (ETX) to avoid blind hop count
problem. With pure hop count, a node
tends to choose the most distance reachable neighbour to minimise the
number of hops, even when the link to that neighbour is noisy and lossy.
The specification also limits $\mathit{Sp}$ to the range $[1, 9]$, so
a candidate parent whose link is too costly cannot be selected.

On the other hand, MRHOF works with any additive metric, such as hop
count, latency or ETX, and uses ETX as default.
Metrics are advertised in the DAG Metric Container option of the DIO
\cite{rfc6551}. For each candidate parent, a node computes the path
cost as the cost of the link to that candidate plus the path cost the
candidate advertises. It then selects the candidate with the lowest
path cost as its preferred parent and derives its own rank from that
path cost, while exclude path cost that exceeds
$\mathit{MAX\_LINK\_METRIC}$ (by default an ETX of 4). MRHOF
introduces hysteresis to avoid to avoid
unnecessary parent switches. A node switches to a new candidate only
if that candidate's path cost is lower than the current parent's by
more than $\mathit{PARENT\_SWITCH\_THRESHOLD}$, which corresponds to
an ETX of 1.5 by default \cite{rfc6719}. Otherwise, the node keeps
its current parent. This prevents the node from switching back and
forth when link metrics fluctuate slightly.

\section{Load Balancing in RPL}
Load balancing is a core technique in distributed systems that spreads
work across multiple equivalent resources, so that the resources are
used efficiently and none of them becomes overloaded. In RPL, load
balancing means spreading the forwarding load (the traffic that nodes
relay toward the root) evenly across the nodes of the DODAG, so that
no single node carries most of it \cite{pancarogluLoadBalancingRPLbased2021}.

There are two problems that most often discussed in the context of
load balancing in RPL: the hot-spot problem and thundering herd problem.

In hot-spot problem, some nodes are chosen as parents more often
than others, especially those near the root as shown in
Figure~\ref{fig:hotspot}. This happens because RPL
uses a single preferred parent for all upward traffic and the
standardised OFs tend to pick up the same "best" routes.
Nodes on those routes carry a large share of the network's traffic
and drain their batteries far faster than their neighbours. This
problem also occurs when nodes generate different amounts of traffic. In
some applications, a few nodes produce much higher traffic than the
rest, for example nodes sending images or video. Thus selecting the
same parent as those high-traffic nodes would exhaust the parent even faster.
Beyond saving energy, balancing the load reduces congestion and queue
overflow at hot spots, which lowers latency and raises the packet
delivery ratio.
\begin{fig}[tbh]
    \begin{center}
        \includegraphics[width=0.5\textwidth]{assets/hotspot.png}
        \caption{Example of the hot-spot problem.}
        \label{fig:hotspot}
    \end{center}
\end{fig}

The thundering herd problem occurs when many nodes react to the same
routing information at the same time and switch to the same parent,
causing their parent choices to oscillate instead of settling. A
typical trigger is a new node joining the DODAG and announcing itself
in a DIO. The new node carries no traffic yet, so it looks like an
ideal parent, and many
neighbouring nodes may switch to it at the same moment. This suddenly
overloads the new node and leaves their previous parent almost idle. When
the previous parent next sends a DIO, it advertises a low load and becomes
the most attractive option again, so the nodes switch back as a group.
Because every node reacts to the same information at the same time, this
cycle can repeat indefinitely as illustrated by
Figure~\ref{fig:thundering_herd}.
The thundering herd problem reduces route stability, which generally
leads to higher control overhead and wasted energy. This happens
because every parent change is a topology change: it resets the Trickle
timer and triggers additional DIO, DAO and DIS messages. Stability can
therefore be measured by the number of control messages transmitted in the
network, where a stable network sends fewer control messages, while an unstable
one sends more.
\begin{fig}[tbh]
    \begin{center}
        \includegraphics[width=0.9\textwidth]{assets/thundering_herd.png}
        \caption{Example of thundering herd problem.}
        \label{fig:thundering_herd}
    \end{center}
\end{fig}

These two problems pose a trade-off that a solution must consider. A
load-balancing mechanism that reacts too quickly to changes
in load causes oscillation like the thundering herd effect, while one that
reacts too slowly leaves hot spots in place. An effective design must therefore
balance responsiveness against stability: it should spread traffic
evenly while suppressing unnecessary parent switches so that the DODAG
remains stable.
